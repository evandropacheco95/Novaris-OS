# api

## Objetivo

Camada de API pública/gateway — ponto de entrada único para integrações externas (SDK, Portal do Desenvolvedor). Também a Composition Root do backend NestJS — único lugar onde implementações concretas de Infrastructure (`PrismaOpportunityRepository`/`PrismaUserRepository`/`PrismaOrganizationRepository`/`BcryptPasswordVerifier`) são instanciadas e conectadas aos Handlers da Application Layer.

## Escopo

**Sales Domain 100% exposto e protegido**: `SalesModule`, com `OpportunityController` expondo os 6 casos de uso — `POST /opportunities` (criar), `GET /opportunities/:id` (buscar), `POST /opportunities/:id/stage` (avançar etapa), `POST /opportunities/:id/proposals` (submeter Proposal), `POST /opportunities/:id/proposals/:proposalId/approve` (aprovar Proposal), `POST /opportunities/:id/won` e `POST /opportunities/:id/lost` (fechar). Prova a arquitetura de ponta a ponta: HTTP → Contracts → Application → Domain → Infrastructure (Prisma) → Postgres real (Supabase) → Contracts → HTTP.

**Identity/Auth MVP (`ENG-0122`)**: `AuthModule`, com `AuthController` expondo `POST /auth/login` (email + senha → JWT). Todas as rotas protegidas por `JwtAuthGuard` (`Authorization: Bearer <token>`). Isolamento de tenant reforçado explicitamente em código (`loadAndAssertOwnership`/filtro por `organizationId`) — achado real desta missão: o role `postgres` usado pelo Prisma tem `rolbypassrls = true`, então as políticas de RLS já escritas não protegem nada nesta API (ver nota em `knowledge/core/DATABASE_ARCHITECTURE.md § 7`). Autenticação apenas por email/senha (bcrypt) — login social (Google/Microsoft) seria um segundo Port futuro, ainda não implementado, exige criação de credenciais OAuth em console externo (ação do CTO, análoga ao setup do Supabase).

**RBAC granular por rota (`ADR-0036`, `ENG-0136`)**: `PermissionGuard` + `@RequirePermission()` (ambos em `AuthModule`), reaproveitando `AuthorizationDomainService` (Identity Domain, implementado desde `EPIC-002`, nunca consultado antes desta missão). Catálogo de 13 códigos de `Permission` — um por Controller protegido (`sales.opportunities.manage`, `relationship.parties.manage`, `relationship.relationships.manage`, `identity.users.manage`, `identity.roles.manage`, `workspace.profile.manage`, `project.projects.manage`, `financial.invoices.manage`, `financial.subscriptions.manage`, `activity.activities.manage`, `marketing.campaigns.manage`, `analytics.dashboards.manage`, `system.audit-entries.read`) — aplicado a todos os 13 Controllers protegidos (`AuthController` permanece público). `apps/api/src/seed.ts` concede o catálogo inteiro a `SuperMaster`/`Usuario`, preservando a paridade de acesso já existente entre as duas Roles — diferenciá-las fica deliberadamente adiado (decisão de produto sem fonte, `ADR-0036`).

**Customer Domain (`ENG-0125`)**: `CustomerModule`, com `PartyController` (`POST`/`GET /parties`, `GET /parties/:id`) e `RelationshipController` (`POST`/`GET /relationships`) — segundo domínio de negócio exposto, mesma receita do Sales. Todos os Handlers de escrita (Sales e Customer) tiveram um bug real corrigido nesta missão (`ENG-0126`): o `Result` de `Repository.save()`/`findById()` não era checado, mascarando falhas reais de infraestrutura como sucesso — corrigido em todos os 8 Handlers de escrita desta API.

**Identity/Organization CRUD (`ENG-0128`)**: `IdentityModule` (`UserController`: `POST`/`GET /users`, `POST /users/:id/activate`, `POST /users/:id/disable`, `POST /users/:id/roles`, `DELETE /users/:id/roles/:roleId`; `RoleController`: `POST`/`GET /roles`, `POST /roles/:id/permissions`, `DELETE /roles/:id/permissions/:code`) e `OrganizationModule` (`OrganizationController`: `GET`/`PATCH /organizations/me`, só a própria Organization do usuário — criar um novo tenant não é operação de usuário logado nesta fase). Domain/Infrastructure de ambos já existiam desde `EPIC-002`/`EPIC-003`/`ENG-0122` — esta missão fechou Application+API.

**Project Domain (`ENG-0130`)**: `ProjectModule` (`ProjectController`: `POST`/`GET /projects`, `GET /projects/:id`, `POST /projects/:id/tasks`, `PATCH /projects/:id/tasks/:taskId`) — terceiro domínio de negócio exposto.

**Financial Domain (`ENG-0131`)**: `FinancialModule` (`InvoiceController`: `POST`/`GET /invoices`, `GET /invoices/:id`, `POST /invoices/:id/pay`; `SubscriptionController`: `POST`/`GET /subscriptions`) — quarto domínio de negócio exposto. `Invoice.markPaid()` dispara `InvoicePaid`, único evento oficial já confirmado em implementação (`DOMAIN_MODEL.md § EVENT BUS`).

**Activity/Marketing/Analytics (`ENG-0133`)**: os 3 penúltimos domínios de negócio. `ActivityModule` (`ActivityController`: `POST`/`GET /activities`, `GET /activities/:id`, `POST /activities/:id/complete`) — único dos 3 com Domain Events (`ActivityCreated`/`ActivityCompleted`). `MarketingModule` (`CampaignController`: `POST`/`GET /campaigns`). `AnalyticsModule` (`DashboardController`: `POST`/`GET /dashboards` — `Widget` não exposto, bloqueado por `ADR-0034`). Achado real corrigido nesta missão: `Activity.create()` não validava `type` em runtime, deixando o CHECK constraint do Postgres devolver 500 em vez de 400 — corrigido com `ValidationError` explícito.

**System/Audit (`ADR-0035`, `ENG-0135`)**: décimo e último domínio de negócio, fechando os 10 Business Domains oficiais. `AuditModule` (`AuditEntryController`: **somente leitura** — `GET /audit-entries`, `GET /audit-entries/target/:targetType/:targetId`; sem `POST`, decisão explícita — uma trilha de auditoria não é fabricável manualmente). Primeira integração real entre um domínio de origem e o Audit Domain: `UpdateOrganizationProfileHandler` (`OrganizationModule`) agora recebe `CreateAuditEntryHandler` injetado (via `AuditModule` importado) e registra um `AuditEntry` real após cada atualização de perfil — mecanismo de enriquecimento decidido em `ADR-0035` (chamada direta via Dependency Injection; falha ao auditar nunca reverte a operação primária).

**Pipeline (`ADR-0051`, `ENG-0160`)**: `PipelineController` (`sales.pipelines.manage`) — `POST`/`GET /pipelines`, `GET`/`PATCH /pipelines/:id`, `POST /pipelines/:id/stages`, `POST /pipelines/:id/stages/reorder`, `PATCH /pipelines/:id/stages/:stageId`. Fecha um gap de auditoria: `Domain`+`Infrastructure` de `Pipeline`/`Stage` já existiam desde `ENG-0043`, mas nunca tinham `Application`/`API` — `Pipeline` ganhou campo `name` (múltiplos Pipelines nomeados por Organização) e `Stage` ganhou campo `order` (reorder real, persistido via `Pipeline.reorderStages()`), decisões de produto do CTO.

Setup local: `pnpm build` (raiz, ordem de dependência via Turborepo) → `pnpm --filter @novaris/api start`. Requer `packages/database/.env` (`DATABASE_URL`/`DIRECT_URL`) e `apps/api/.env` (`JWT_SECRET`) configurados — ambos carregados automaticamente por caminho absoluto, independente do `cwd`. Seed de bootstrap: `node dist/seed.js` (idempotente — cria a Organization "novaris" e os 2 primeiros Users se ainda não existirem).
